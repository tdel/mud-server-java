## Project
This project is a game. It was originally built around DnD5e (Dungeon and Dragon 5th edition) rules, and several systems still are.

**Exception (races/classes/leveling)**: races, classes and the level cap deliberately deviate from strict SRD compliance since the "human-only, Fighter/Mystic + subclasses" refactor — see the "Notes for this project" sections of `docs/dnd5e/races.md`, `classes.md`, `leveling-xp.md`. Character build/progression is closer to a Lineage2/Ragnarok Online style.

**Exception (combat)**: combat itself (attack roll, damage, defense) is no longer DnD5e at all — it was replaced by a Lineage2-style model (p.atk/p.def/m.atk/m.def, accuracy/evasion, criticalRate; STR/DEX/CON/INT/WIT/MEN attributes, WIT/MEN being the renamed Wisdom/Charisma). Max HP/mana and their regen followed the same move (CON/MEN-driven, see `docs/lineage2/combat.md`'s "Health & Mana pools"). See `docs/lineage2/README.md` for the current combat rules and `docs/dnd5e/combat.md`'s "Notes for this project" for what it replaced. Skill/saving-throw checks, resting, and XP/leveling stay DnD5e-compliant (see `docs/dnd5e/`).

## DnD5e rules reference

`docs/dnd5e/` holds a scoped, per-system summary of the DnD5e SRD rules (sourced from the official CC-BY-licensed SRD 5.1), each file ending with a "Notes for this project" section tying the rule to the current implementation. Load only the file(s) relevant to the system being touched — don't read the whole directory speculatively. Start from `docs/dnd5e/README.md` for the full index (`combat.md` and `spellcasting.md` are the two most likely to be relevant now that both systems are implemented, see below).

## Build, test, run

Java 25 (Temurin) and Maven are installed on the host directly (e.g. via SDKMAN: `sdk install java 25-tem`, `sdk install maven`) — no Docker involved:

```
mvn <goal>
```

Substitute `<goal>` with:

- `package` — build
- `spring-boot:run` (or run the packaged jar directly) — run the app
- `test` — run tests
- `spotless:apply` / `spotless:check` — format / verify formatting. `check` also runs automatically in the `verify` phase (not `test`). Uses the Eclipse formatter, not google-java-format — google-java-format's javac-internals dependency is currently broken on Java 25 ([diffplug/spotless#2468](https://github.com/diffplug/spotless/issues/2468)).

A `Makefile` wraps the same goals (`make package|test|run|format|format-check|clean`) plus `make install-linux` (idempotent SDKMAN/Java 25/Maven bootstrap) — it hardcodes `JAVA_HOME`/`PATH` to SDKMAN's "current" symlinks since `make` runs recipes in a non-interactive shell that never sources `~/.bashrc`.

The game protocol is JSON over raw TCP, listening on port **4002** (`app.tcpjson.port` in `application.yml`). A second port, **8081** (`management.server.port`), serves Spring Boot Actuator (`/actuator/health`, `/actuator/info`, `/actuator/metrics` only — see `management.endpoints.web.exposure.include`); it's the only HTTP surface in the project, added solely to carry Actuator since the game protocol itself stays raw TCP/JSON.

## Stack specifics

- Java 25, Spring Boot 4.1.0. Persistence is jOOQ (`DSLContext`, `spring-boot-starter-jooq`) — a type-safe SQL builder, not an ORM: no persistence-context, no lazy loading, no dirty-checking. Chosen over JPA/Hibernate specifically because DAO call sites never run inside a transaction except a handful of `@Transactional` `@EventListener`s (see "Domain model & events" below), which would fight an ORM's session/entity-lifecycle assumptions.
- Storage is a single **SQLite** file (`org.xerial:sqlite-jdbc`, `spring.datasource.url: jdbc:sqlite:./mud-server.db`), not a server process — chosen specifically to cut local/CI bootstrapping to zero (no container, no daemon). HikariCP pool is capped at 1 connection (`spring.datasource.hikari.maximum-pool-size`) since SQLite doesn't support concurrent writers, which costs nothing here given the server is already single-process. Foreign keys are off by default in SQLite and are re-enabled per-connection via `spring.datasource.hikari.connection-init-sql: "PRAGMA foreign_keys = ON"`.
- The DSL classes (`persistence.jooq.tables.*`, `persistence.jooq.tables.records.*`) are generated at build time (`generate-sources` phase, `jooq-codegen-maven`) directly from the Flyway migration files (`V1__init_schema.sql` … `V18__rename_zone_to_map.sql`) via `org.jooq.meta.extensions.ddl.DDLDatabase` — **no live database connection is needed for codegen**, it parses the Flyway SQL files themselves. Flyway stays the single source of truth for the schema; jOOQ only reflects it. The plugin's `scripts` property is an Ant-style glob (currently `V*.sql`, matched via `org.jooq.FilePattern` — not a comma-separated list), sorted with `sort=semantic` so `V2` is read after `V1`; a new migration file just needs to match the same `V*.sql` pattern to be picked up, no pom.xml change required.
- SQLite's `ALTER TABLE` only supports `RENAME TABLE`/`RENAME COLUMN`/`ADD COLUMN`/`DROP COLUMN` — no `ADD CONSTRAINT`, no `ALTER COLUMN`, and `UNIQUE`/`CHECK` constraints can't be `DEFERRABLE` (only foreign keys can). Migrations that need to add a constraint after the fact (tighten a column to `NOT NULL`, add a `UNIQUE`) have to rebuild the table (`CREATE TABLE x_new (...)`, `INSERT INTO x_new SELECT ... FROM x`, `DROP TABLE x`, `RENAME TABLE x_new TO x`, then recreate any indexes lost with the drop) — see `V8__add_character_world_instance.sql` for the pattern. Where a constraint isn't worth a full rebuild, it's dropped in favor of purely application-level validation instead, same convention used for FKs into file-backed data (map/item-template ids, see below). Conversely, a migration that only *removes* a column/table (`DROP COLUMN`, `DROP TABLE`) needs no rebuild at all, even on a column/table involved in an FK — see `V11__remove_item_room.sql`/`V12__remove_multi_world.sql`.
- DAOs (`persistence/*Dao`) keep a stable public API (`insert`/`findById`/etc.) regardless of the underlying query engine — internals use `dsl.selectFrom(TABLE)...fetch(RowMapperEquivalent)` with a small `private static toDomain(...)` mapper per DAO.
- Boot 4 split several things out of core that older Boot versions bundled: Flyway needs the dedicated `spring-boot-starter-flyway` (plain `flyway-core` isn't enough) plus `flyway-database-nc-sqlite` (version pinned manually in `pom.xml` — unlike the historical `flyway-database-postgresql`, it isn't managed by the Spring Boot BOM); Jackson's `ObjectMapper` bean comes from `spring-boot-starter-json`.
- Boot 4.1 pulls in **Jackson 3**, not the historical Jackson 2 — the package root is `tools.jackson.*` (e.g. `tools.jackson.databind.ObjectMapper`), not `com.fasterxml.jackson.*`. Easy to get wrong from memory/muscle-memory; check an existing import (e.g. `network/server/tcpjson/TcpJsonServer.java`) before writing a new one.
- `spring-security-crypto` is used only for BCrypt — not the full Spring Security starter.
- **One transport**, TCP/JSON (`network/server/tcpjson`), the only client protocol in the project — no telnet, no text prose (an older telnet-based iteration is gone; don't trust references to it in `TODO.md`, which predates the current architecture and is not kept in sync — see "Stale docs" below). `network/OutputMessage` is a marker interface; `network/OutputJsonMessage` (`toJson(TcpJsonOutput)`) is the rendering contract, implemented by every record under `network/message/**`. Nothing under `domain`/`game` imports `network.server.*`. The long-term plan is also a graphical 2D/2.5D client (Godot or Unity, undecided) talking a different protocol — the Tiled-authored maps (see below) are already a step in that direction; keep new `domain`/`game` code free of transport-specific concerns so future swaps stay contained. `OutputJsonMessage.toJson` has a **default implementation** that serializes the record as-is via Jackson (records serialize natively, no annotations needed) — so most of the 114+ records under `network/message/ingame/` need no method body at all, just `implements OutputJsonMessage` in the type header. Only records that embed a domain object instead of plain value fields (e.g. `MapView`, `GamePlayerStats`, `MonsterStatBlock`, `EntityView`) override `toJson` to build a small nested DTO instead of serializing the domain object graph. `network/server/tcpjson/TcpJsonConnection.send()` throws if a message doesn't implement `OutputJsonMessage` — the default method just means that never happens in practice.
- `CommandHandler` (`network/CommandHandler.java`) has a `requiresAlive()` default method (`false`) that a handler overrides to `true` to be rejected while the character is dead (e.g. `Attack`) — checked by `CommandDispatcher` before `onReceive` runs.

## Domain model & events

- Domain objects are plain POJOs, never Spring beans, and carry their own business logic rather than being anemic data holders pushed around by Services. The actor hierarchy lives under `domain/actor`: `AbstractCharacter` (base: HP, position, current map/zone, attributes) → `AbstractNpc`/`CharacterInstance` (player character, `domain/actor/instance/CharacterInstance.java`) /`MonsterInstance`/`NpcSellerInstance` (`domain/actor/instance/*`), plus `domain/actor/template/{MonsterTemplate,NpcTemplate}` for the file-backed rules data behind an instance. Per-character *behavior* is split into small composed components under `domain/actor/component/`: `CharacterCombat` (attack resolution, target, cooldown), `SpellCasting` (known spells, cast resolution, per-spell cooldown), `ActiveEffects`/`ActiveEffect` (timed buffs/debuffs), `PlayerInventory` (items/gold) — `CharacterInstance.getCombat()`/`getSpellCasting()`/`getActiveEffects()`/`getInventory()` expose them. None of these hold a DAO reference, which is what makes them unit-testable without Spring or a database.
- Because these objects aren't Spring-managed, they can't get a constructor-injected `ApplicationEventPublisher`. `domain/actor/event/DomainEventPublisher` is a static holder around Spring's publisher instead, initialized once at startup by `config/DomainEventPublisherInitializer` — well before any domain mutation is possible (that only happens while handling a client command or a `@Scheduled` engine tick, i.e. after the context is fully up).
- Every business mutation applies the in-memory change first, then calls `DomainEventPublisher.publish(...)` with an event record from `domain/actor/event/*` (one file per event — combat: `AttackBegin`, `MonsterAttacked`, `CharacterDied` (a monster dying), `GamePlayerDied`/`GamePlayerDamaged`/`GamePlayerRespawned`; spells: `SpellCastBegin`, `SpellCast`, `CharacterLearnedSpell`, `CharacterEffectExpired`; movement: `CharacterStartedMoving`/`CharacterStoppedMoving`, `GamePlayerMovedToMap`/`GamePlayerSpawnedToMap`; items/gold: `ItemDiscarded`, `GamePlayerEquippedItem`/`GamePlayerUnequippedItem`, `CharacterLootedItem`, `ItemPurchased`, `CharacterReceivedGold`/`CharacterSpentGold`; progression: `CharacterGainedXp`, `CharacterLeveledUp`; lifecycle: `NewGamePlayerCreated`, `PlayerLoadedInWorld`/`PlayerRemovedFromWorld`, etc).
- `@EventListener` methods (in `persistence/listener/*` — `ItemPersistenceListener`, `CharacterPersistenceListener`, `SpellPersistenceListener`, `ActiveEffectPersistenceListener`, `WorldInstancePersistenceListener` — plus a few `game/engine/*` engines) are the *only* places that write to the DB — a listener never contains the business rule itself, only the persistence of a fact the domain object already applied. Dispatch is deliberately synchronous (plain `@EventListener`, no `@Async`). `@Order` is used sparingly, only where message/effect ordering matters (e.g. `CharacterPersistenceListener.onCharacterDied` is `@Order(2)` to run after other death-related listeners). Currently `@Transactional`: `ItemPersistenceListener.onGamePlayerEquippedItem` (both `updateSlot` calls it triggers commit together), `SpellPersistenceListener` (learning a spell + persisting it), and `game/engine/RegenHealthEngine.onCharacterDied`.

## Persistence: SQLite vs classpath JSON/Tiled

Two kinds of data live in two different places, split by nature (static rules vs. in-play mutable state), not by convenience:

- **Classpath JSON** (`src/main/resources/data/{levels,monsters,npcs,race,class,spells,world}.json` plus `data/items/{consumables,armors,weapons,others}.json`), loaded once via Jackson `ObjectMapper` during warm-up (see below), never written back, and never represented in the Flyway migrations. This is game-content/rules data: item/monster/npc templates, race/class definitions, the XP table, the spell catalog, and `world.json` (the single `WorldTemplate` descriptor). Item templates are split by category rather than one `items.json` because the shape genuinely differs: `EquipmentItem` (armors/weapons — combat stats, `armorCategory`, `atkSpd`, granted spells, elemental resistances, set id) vs the plain `ItemTemplate` base used for consumables (`ConsumableItem` — potion effect data only, no combat stats; food/`FOOD` was removed as unused) and others (`KEY`/`TOOL`/`MISC`, currently empty) — see `ItemTemplateCatalog.warmItemTemplates` for the per-file DTOs. Monster loot tables (`monsters.json`) reference item template ids; an item only comes into existence when a `LootTableEntry` hits, a shop sale happens, or a monster grants gold — `MonsterTemplate.grantLootTo` is called from `RegenHealthEngine.onCharacterDied` (see below), so this path does run on every monster kill, not just XP.
- **Classpath Tiled maps** (`src/main/resources/data/maps/*.tmx`), one file per map, authored in the [Tiled Map Editor](https://www.mapeditor.org/) and parsed at warm-up by `game/catalog/tiled/TiledMapLoader` (hand-rolled XML parsing via `org.w3c.dom`, **no Tiled/TMX library dependency** in `pom.xml`) into a `domain/world/MapTemplate`: terrain/collision (`CollisionGrid`, from tile properties), spawn position, monster/NPC spawns, portals to other maps (`MapTemplatePortal`), and peace-zone polygons (see below). `game/catalog/tiled/{TiledMap,TiledCoordinateMapper}` hold the intermediate parsed representation before `TiledMapLoader.parse` builds the domain objects.
- **SQLite via jOOQ** (`persistence/*Dao`: `AccountDao`, `CharacterDao`, `ItemDao`, `CharacterSpellDao`, `CharacterActiveEffectDao`): state that changes during play — accounts, a character's position/HP/mana/XP/gold, known spells, active timed effects, and item *instance* ownership/equipped slot. Item *templates* are file-based rules data; item *instances* (who holds one, what slot) are DB rows that get a file template attached onto them in memory. An `Item` only ever exists in a loot table (file-based, not yet materialized) or in a player's inventory (`character_id` set) — it can never be "on the ground" on a map; `drop` (`CharacterInstance.discardItem`, event `ItemDiscarded`) permanently destroys an item instead of placing it somewhere else.
- The two are stitched together by the event pattern above: `@EventListener` methods are the only point where in-memory state (whether it originated from a file, a `.tmx`, or the DB) gets pushed to SQLite.

## Warm-up & in-memory caches

- `ServerApplication.warmupRunner` (an unconditional `ApplicationRunner` bean — deliberately not gated on the transport's `enabled` flag, since warm-up is transport-independent) runs after the Spring context refreshes but before `ApplicationReadyEvent`/`TcpJsonServer.start()`. This ordering is a Spring Boot lifecycle guarantee (`ApplicationRunner` beans always run before `ApplicationReadyEvent` is published), not something wired manually. Call order is significant and documented inline in `ServerApplication`: **spells → item templates → world/map templates → monsters → XP thresholds → `materializeDefaultWorld()`**. Spells load first because `ItemTemplateCatalog` denormalizes the armor/weapon `grantedSpellIds` into `Spell` objects via `SpellCatalog.getById` at load time (magic gear granting a spell); item templates load before the world materializes because character creation (`WorldInstance.createCharacter`) learns level-1 spells via `SpellCatalogHolder` as soon as the default world exists.
- The warm-up singletons live under `game/catalog/` and are all named `*Catalog` (not `*Service`): `ItemTemplateCatalog`, `LevelCatalog`, `MonsterCatalog`, `NpcCatalog`, `SpellCatalog` (+ `SpellCatalogHolder`, a static holder analogous to `DomainEventPublisher`, initialized by `config/SpellCatalogHolderInitializer` so non-Spring domain code — e.g. `WorldInstance.createCharacter` — can look up a `Spell` by id), `WorldTemplateCatalog`. Each holds a `ConcurrentHashMap` populated once and never invalidated or reloaded. A single, global `WorldInstance` (id `WorldInstance.DEFAULT_ID`) is materialized once at warm-up by `WorldInstanceService.materializeDefaultWorld()` (`game/WorldInstanceService.java`) and held for the whole process lifetime — there is no per-account/per-party world selection (see "Party system" below for why `Party` still exists despite this). A `MapInstance` (built from a `MapTemplate`) lives as exactly one instance per map for the whole process lifetime; an `Item` only lives in memory inside a player's `PlayerInventory` once loaded, never in a shared/warmed cache.
- This is a deliberately simple, **single-process** model: there's no invalidation and no cross-instance synchronization if the server were ever split across multiple processes. Treat this as a known simplification likely to need rework before any horizontal scaling, not as a settled design decision.

## Concurrency: connections + scheduled engine ticks

- `config/VirtualThreadExecutorConfig` exposes one shared `Executors.newVirtualThreadPerTaskExecutor()` bean. Never block JDBC or other blocking logic on Netty's NIO threads.
- `network/server/tcpjson/TcpJsonSessionHandler` spawns **exactly one virtual thread per connection**, which loops `inbox.take()`-ing from a `LinkedBlockingQueue<String>` fed by `channelRead0`. Do **not** submit each incoming line independently to the executor — two lines arriving in the same TCP packet could then run on different virtual threads with no ordering guarantee. The single-consumer queue is what preserves per-connection command ordering. A player is only ever driven by its own connection, so no two threads can mutate the same character's state concurrently *from the command side* (this silently depends on "one connection per account" actually holding — see the known double-login race, cross-referenced below).
- Since the real-time combat/spell/movement rewrite, a **second concurrency dimension** exists: `config/SchedulingConfig` (`@EnableScheduling`, a 10-thread `ThreadPoolTaskScheduler`) backs a family of `@Scheduled(fixedRate = ...)` "engines" under `game/engine/` — `MovementEngine` (100ms tick, steps characters along waypoints), `SpellCastEngine` (resolves a cast once its casting time elapses), `ActiveEffectEngine` (expires timed buffs/debuffs), `RegenHealthEngine`/`RegenManaEngine`, `MonsterAiEngine` (aggro/chase), `MonsterRespawnEngine`, `ProjectileEngine` (spell projectiles), `PartyEngine` (invite-timeout expiry). Each engine tracks its own working set in a `ConcurrentHashMap<UUID, AbstractCharacter>` populated/cleared via `@EventListener`s. This means a background tick can now run concurrently with that same character's own command thread (e.g. a movement tick landing while the player issues `attack`) — two different mitigations coexist for this, neither applied everywhere: `CharacterCombat` (target/`nextAttackAt`) and `SpellCasting` keep their per-combat/cast state in `volatile` fields with no lock, while `MovementEngine.startMovement`/`stopMovement` (and its tick) guard `AbstractCharacter.activeMovement` with `synchronized (character)`, `MonsterInstance` guards its own state with `synchronized (this)`, and `KnownList`/`AbstractCharacter.broadcast` guard perception refresh with `synchronized (map)`. Treat this as the current, not-fully-audited concurrency model — same spirit as the double-login gap, not a settled guarantee.
- `equipItem` publishes one `GamePlayerEquippedItem` event carrying both the newly-equipped item and any previous occupant of the same slot, so `ItemPersistenceListener.onGamePlayerEquippedItem` (`@EventListener` + `@Transactional`) can apply both `updateSlot` calls in one transaction — the previous occupant is always cleared before the new slot is assigned, so the two updates never collide even without a deferred DB constraint (`uniq_character_slot` in `V1__init_schema.sql` is a plain, non-deferred `UNIQUE` — SQLite doesn't support deferrable `UNIQUE` constraints at all).

## Test context gotcha

`TcpJsonServer.start()` hands its `bind().sync()` / `channel.closeFuture().sync()` sequence to the shared `virtualThreadExecutor` and returns immediately from the `@EventListener(ApplicationReadyEvent.class)` method — this is what lets the listener return promptly instead of blocking for the process lifetime. A `@SpringBootTest` therefore won't hang at context startup, but it will still bind a real TCP port as a side effect; set `app.tcpjson.enabled=false` in test config to avoid that (once a `src/test/resources/application.yml` exists — none does yet; `src/test` currently only has 3 plain domain unit tests: `AbstractCharacterZoneTest`, `MapTemplateTest`, `PeaceZoneTest`). No Testcontainers/Docker dependency for a future `@SpringBootTest`: SQLite is a plain file, so pointing `spring.datasource.url` at a temp file or `jdbc:sqlite:file::memory:?cache=shared` (plain `:memory:` gives each connection its own private DB, wrong for a pool — `cache=shared` is what makes an in-memory SQLite DB visible across connections) is enough.

## Conventions

- Package-by-feature at the top level (`config`, `domain`, `game`, `network`, `persistence`), package-by-layer within. The transport lives under `network.server` (`network.server.tcpjson`); command handlers live under `network.command`. Domain entities and outbound network messages are Java `record`s (except the actor/component classes above, which need mutable identity/state).
- One `CommandHandler` class per in-game command verb under `network/command/{connected,charselect,ingame}`, auto-discovered by `CommandRegistry` (constructor-injected `List<CommandHandler>`, no manual registration), paired with a response `record` under `network/message/**`. Use `/add-command` to scaffold a new one; use `/add-domain-event` to scaffold a new domain event + publishing method + persistence listener.
- Commit messages: French, no phase-numbering scheme (earlier history used "Phase N : ..." — don't continue that numbering).
- Use logging (SLF4j) as much as possible in order to know what's going on.
- Don't need to add javadoc.

## Combat & spellcasting (real-time, not turn-based)

The old turn/initiative engine (`domain/combat/ActionEconomy`, `CombatEncounter`, `game/CombatEngine`) is gone for good; combat and spellcasting were rebuilt from scratch as **real-time, cooldown-driven** systems — there is no round counter or action economy anywhere in the current code.

- **Melee** (`network/command/ingame/Attack.java` → `CharacterInstance.getCombat().attack(target)`, `domain/actor/component/CharacterCombat.java`): rejects if the caster is casting a spell, has no/dead/an NPC target, either side is standing in a `PeaceZone`, target is out of `MonsterAiEngine.ATTACK_RANGE`, or the attacker is still on `ATTACK_COOLDOWN` (2s, `isReady()`/`remainingCooldown()`). Otherwise resolves a Lineage2-style hit (`game/combat/CombatFormulas`: hit chance from accuracy vs the defender's evasion, independent critical roll, damage from a p.atk/p.def ratio + random variance — see `docs/lineage2/combat.md`), applies damage, and broadcasts `AttackResult`.
- **Spells** (`Cast.java` → `SpellCasting.cast`, `domain/actor/component/SpellCasting.java`, catalog in `data/spells.json` via `SpellCatalog`): casting isn't instant — `SpellCastEngine.beginCast` records an `ActiveCast` (spell + target + start time + casting-time), and its own `@Scheduled` tick resolves it once elapsed (`resolveCast`), re-validating the target is still valid at that point. Effect types include damage (same accuracy/evasion hit check, then a m.atk/m.def ratio scaled by the spell's `effectDice` — see `docs/lineage2/combat.md`), heal, and timed buff/debuff (`ModifiedStat`), tracked per-target by `ActiveEffects`/`ActiveEffect` and expired by `ActiveEffectEngine`'s tick (`CharacterEffectExpired` → `SpellModifierExpired`/`PartyMemberEffectExpired`). Each known spell has its own cooldown (`SpellCasting.isReady`/`remainingCooldown`), separate from `CharacterCombat`'s melee cooldown. `SpellLearningEngine`/`CharacterLearnedSpell` handle gaining new spells (currently just level-1 spells at character creation).
- **Peace zones** (`domain/world/PeaceZone`/`AbstractZone`/`NormalZone`): a `PeaceZone` is a named polygon (ray-casting point-in-polygon test) drawn as an object layer in a map's `.tmx` file and parsed by `TiledMapLoader`; entering/exiting one sends `PeaceZoneEntered`/`PeaceZoneExited`, and both melee and (implicitly, via the same `getZone()` check pattern) ranged/spell combat are blocked there (`CombatForbiddenHere`). `MapTemplate.zoneAt(position)` falls back to `NormalZone.INSTANCE` when no `PeaceZone` polygon contains the position.
- **Death & loot**: killing a monster publishes `CharacterDied`; `game/engine/RegenHealthEngine.onCharacterDied` (`@Transactional`) removes the monster from its `MapInstance`, then computes the killer's party (members present on the killer's map, `party.shareMultiplier(size)`) and calls `MonsterTemplate.grantLootTo` (gold + `LootTableEntry` rolls) for that group inline — this is a documented exception to "a listener only persists a fact the domain object already applied" (see "Domain model & events" above). XP is granted separately via `CharacterPersistenceListener.onCharacterDied`, also split across the party.

## Maps & movement

Movement moved from the old hexagonal-grid system (`domain/HexCoordinate`, `RoomPortal`, `game/HexGridRenderer` — all gone) to **Tiled-authored tile maps with continuous, waypoint-based real-time movement**:

- Maps are authored as `.tmx` files in `data/maps/*.tmx` (Tiled Map Editor), parsed once at warm-up by `TiledMapLoader` into an immutable `MapTemplate` (id, name, `CollisionGrid`, spawn position, monster/NPC spawns, `MapTemplatePortal`s, `PeaceZone` polygons); a `MapInstance` wraps a `MapTemplate` for the live, single global `WorldInstance`.
- `domain/map/GridPathfinder` runs an A*-like search (`findCellPath`, octile heuristic, diagonal moves blocked if both orthogonal neighbors are non-walkable) over the map's `CollisionGrid` to turn a destination click/command into a list of waypoints.
- `game/engine/MovementEngine` (100ms tick) then steps a character continuously along those waypoints — speed is `unitsPerSecond(speed) = max(1, speed) / SPEED_DIVISOR` (DnD5e speed stat driving real-world movement rate), publishing `CharacterStartedMoving`/`CharacterStoppedMoving` and `CharacterMovementStarted`/`Finished`/`Stopped`/`Blocked` as it goes. `startMovement`/`stopMovement` are the entry points a command handler (`Goto`) calls; `onAttackBegin` stops movement so you can't walk and swing at once.
- Portals (`MapTemplatePortal`, command `Portal`) move a character between two `MapInstance`s (`GamePlayerMovedToMap`/`SpawnedToMap`, `MapEnter`).

## Party system

`domain/Party.java` is an **in-game grouping** (leader, members, a `LootMode` — round-robin or leader-only — `shareMultiplier` for split XP) managed via `network/command/ingame/Party{Invite,Accept,Decline,Kick,Leave,Disband,Loot}.java` and `game/engine/PartyEngine` (a `@Scheduled` tick that expires pending invites after `INVITE_TIMEOUT_MS`, plus cleanup on `PlayerRemovedFromWorld`). This is **unrelated** to the old multi-world `LOBBY`/per-account `WorldInstance` selection feature (which *was* called "Party" too, back when the whole lobby/multi-world layer existed) — that layer was removed in `V12__remove_multi_world.sql` and login now goes straight to `CHARSELECT`. The current `Party` only exists to group characters *within* the single global world for shared XP/loot — don't confuse the two if you find references to the old one in git history or in `TODO.md`.
